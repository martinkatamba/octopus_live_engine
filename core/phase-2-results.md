# Phase 2: FFI and Python spike, results

The question for phase 2 was whether the Rust core is worth putting under the
Python SDK: does calling it from Python cost more than it saves? This page has
the measurements and a recommendation. The plan is in [plan.md](plan.md).

**Update, 2026-10-29: the decision is go.** The condition below has been met
(the core's per-step cost was fixed). The new numbers are in
[After the per-step fix](#after-the-per-step-fix).

## What was built

- **The C ABI** (`crates/octopus-ffi`):
  - every function in the contract, with a status code on each call and the
    last error kept per thread;
  - no panic crosses the boundary;
  - activity callbacks may run on any core thread;
  - the header `include/octopus.h` is generated by cbindgen.
  - `scripts/check-ffi.sh` checks that the header is current, then builds
    and runs a C program against it (`tests/c/smoke.c`).
- **The Python binding** (`bindings/python`, PyO3 0.29):
  - Python values convert directly to the core's values, with no JSON text in
    between;
  - runs release the GIL;
  - each activity call takes the GIL back on whichever thread the core uses.
  - `octopus_core.fastapi` mounts declared routes and the diagram on FastAPI.
- **Route rules moved into the core** (`domain/services/routes.rs`):
  - which client job ID to trust;
  - what a declared route answers (D5);
  - how a failed run is reported.

  `../rust`, the C ABI and Python all use them.

**`order_fulfillment_api` runs on the core.** The test loads the example's
`server.py`, so it uses the example's own activities and its blueprint,
including SQLite persistence. It passes 6 checks:
- the example's three HTTP tests;
- the same response body as the pure-Python engine, for both orders;
- the async notification step runs.

## Measurements

| | |
|---|---|
| Machine | Intel i7-7660U, 4 cores, macOS 13.7, Python 3.12.3 |
| Builds | release builds of the core and the C ABI library |
| Load average | 14 → 12. The machine was busy (4 cores), so absolute times are inflated |
| Method | 10 rounds × 100 runs per engine and workload. Engines take turns within each round, so load affects them alike. Before timing, every engine had to record the same traces and status |
| Raw data | [bindings/python/bench/results.json](bindings/python/bench/results.json) |

The three engines:
- **python** is the current `octopus_live` engine.
- **core (PyO3)** is the binding Python will use.
- **core (C ABI)** is the C ABI called through ctypes, with JSON text both
  ways. It stands in for the .NET, Java and Go hosts.

The order workflows have the example's persistence and `mode: hybrid`
removed, so every engine uses its in-memory store and none replicates to
Temporal. With `mode: hybrid` left in, the Python engine spends about 5 s per
HTTP request trying to reach Temporal.

| Workload | Activity calls | python | core (PyO3) | core (C ABI) |
|---|---:|---:|---:|---:|
| 1 no-op step | 1 | 505 µs | 193 µs (2.6×) | 311 µs (1.6×) |
| 10 no-op steps | 10 | 2,867 µs | 602 µs (4.8×) | 1,007 µs (2.8×) |
| 50 no-op steps | 50 | 28,916 µs | 2,489 µs (11.6×) | 5,592 µs (5.2×) |
| Order, 1 item | 5 | 4,962 µs | 2,406 µs (2.1×) | 2,982 µs (1.7×) |
| Order, 10 items | 14 | 14,576 µs | 19,465 µs (**0.7×**) | 24,533 µs (**0.6×**) |
| Order, 1 item, through FastAPI | 5 | 10,058 µs | 8,146 µs (1.2×) | — |

These are medians; p95s are in the raw data. The multipliers are speed-ups
over python. Called directly, the order's own activities cost 6.9 µs per run,
so the times above are almost all engine.

**Per step:**
- **The core costs about 50–60 µs per no-op step through PyO3**, and about
  100 µs through the C ABI. That includes crossing the boundary and taking
  the GIL back.
- **The Python engine costs about 290 µs per step at 10 steps and 580 µs at
  50.** It slows down as a run gets longer.

## Where the core's time goes

On the 10-item order the core is slower than Python. A sample profile (macOS
`sample`, 895 runs) splits the core's time like this:

| Share | What |
|---:|---|
| ~46% | `PipelineManager::save` → `snapshot`: copying and masking the whole job after every step |
| ~8% | `publish_event`: each step's live event turns the state into JSON |
| ~26% | cloning and freeing `ExecutionState` and `StepExecutionTrace` values |
| ~9% | masking each step's payload and turning traces into JSON values |
| ~5% | `run_activity`: the Python call, including the conversion both ways |

The shares are of the samples under `run_steps`.

**The boundary is not the problem.** The core's own bookkeeping is.
- Every trace keeps copies of its step's input and output.
- The whole job is copied after each step.

So a run's cost grows with steps × job size. The 10-item loop is 14 steps over
a job that grows with each reservation.

Smaller hot spots seen in the same profiles:
- each async step starts a new OS thread (`run_with_retry`);
- each new job ID opens `/dev/urandom`.

## Recommendation: go, with one condition

**Go:**
- The boundary costs microseconds per step, and through PyO3 it is cheaper
  than the Python engine's own per-step work.
- Short and medium workflows, which is most API traffic, are 2–12× faster on
  the core.
- The example runs unchanged on the core and gives the same answers.
- The C ABI works from C and from ctypes, which is the evidence available
  here for .NET, Java and Go.

**The condition:** before phase 3 switches the Python SDK, make the core's
per-step cost stop growing with the job's size. Then rerun the 10-item order,
and then 50- and 100-item loops. The fix is in the core, so every SDK gets it.
Possible ways to do it:
- save only what changed;
- share trace payloads instead of copying them (`Arc`);
- build an event's JSON once, and only when someone is subscribed;
- reuse dispatcher threads.

The conformance suite guards the behaviour while doing it.

**Not measured yet:**
- the Python engine with its real SQLite store against the core's;
- memory use;
- many concurrent requests. Releasing the GIL should help the core there,
  which is worth showing;
- a quiet machine.

## After the per-step fix

The core no longer deep-copies the job. Its maps are copy-on-write and
masking shares what it doesn't change. Details are in [done.md](done.md).

**Machine and method:** the same machine and method as above, at load 8 → 5
(quieter than before, so compare the engines with each other rather than
with the first table). The order's loop was allowed 1000 items so the large
orders reserve every item. Raw data:
[bindings/python/bench/results.json](bindings/python/bench/results.json).

| Workload | Activity calls | python | core (PyO3) | core (C ABI) |
|---|---:|---:|---:|---:|
| 1 no-op step | 1 | 354 µs | 48 µs (7.4×) | 110 µs (3.2×) |
| 10 no-op steps | 10 | 1,833 µs | 203 µs (9.0×) | 435 µs (4.2×) |
| 50 no-op steps | 50 | 19,984 µs | 767 µs (26×) | 1,737 µs (11.5×) |
| Order, 1 item | 5 | 3,089 µs | 490 µs (6.3×) | 861 µs (3.6×) |
| Order, 10 items | 14 | 9,414 µs | 1,540 µs (6.1×) | 3,151 µs (3.0×) |
| Order, 50 items | 54 | 52.8 ms | 15.8 ms (3.3×) | 35.7 ms (1.5×) |
| Order, 100 items | 104 | 143 ms | 73 ms (2.0×) | 146 ms (1.0×) |
| Order, 1 item, SQLite store | 5 | 7,663 µs | 1,364 µs (5.6×) | — |
| Order, 1 item, through FastAPI | 5 | 6,225 µs | 3,568 µs (1.7×) | — |

**With 8 orders in flight** (runs per second; threads for the core, asyncio
tasks for the Python engine):

| Workload | Engine | 1 in flight | 8 in flight |
|---|---|---:|---:|
| Order, 1 item | python | 309 | 250 |
| Order, 1 item | core (PyO3) | 1,762 | 2,036 |
| Order, 10 items | python | 95 | 84 |
| Order, 10 items | core (PyO3) | 620 | 512 |

**What the numbers show:**
- **The 10-item order is now 6× faster on the core**, where before it was
  slower than Python.
- **Concurrency adds little.** The activities are Python, so they take turns
  holding the GIL.

**What still grows with the payload: the boundary.**
- Pure Rust: the 100-item order takes 1.85 ms (`examples/bench_order.rs`).
- Through PyO3: 73 ms.

The difference is that each activity call converts the job's whole payload
to Python and back, and the returned state converts every trace's input.
The core is still faster than Python at every size, but this is the next
thing to fix (to-be-done.md).

**After converting shared maps once** (done.md), the PyO3 numbers at load
14 → 6 were:

| Order | Before | After | Python engine |
|---|---:|---:|---:|
| 10 items | 1,540 µs | 1,184 µs | 10,184 µs |
| 50 items | 15.8 ms | 11.2 ms | 59.1 ms |
| 100 items | 73 ms | 42 ms | 154 ms |

What is left is copying each activity's payload into Python and back.

The C ABI writes JSON text, which can't share, so the fix doesn't reach it:
at 100 items it is no faster than the Python engine.
